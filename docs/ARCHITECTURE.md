# Архитектура решения

## Из чего состоит

Три пакета ROS 2 в одном воркспейсе `ros2_ws`:

| Пакет | Что внутри | Зачем отдельно |
|---|---|---|
| `rail_guard_msgs` | `Obstacle`, `ObstacleArray`, `GaugeStatus`, `TrackCorridor` | интерфейс к смежным подсистемам; собирается без Python-зависимостей, поэтому его может подключить любой потребитель |
| `rail_guard` | `lib/` — алгоритм без ROS, `nodes/` — две ноды | алгоритм тестируется и профилируется без транспорта: те же объекты крутятся в ноде и в офлайн-прогоне |
| `rail_guard_bringup` | launch-файлы, профили параметров, конфигурация RViz | настройка под линию отделена от кода: под другую линию меняется YAML, а не исходники |

## Как идут данные

```
                    ┌──────────────── rosbag2 / драйвер лидара
                    │                 sensor_msgs/PointCloud2, 10 Гц
                    ▼
            /lidar_points (имя любое — детектор находит облако сам)
                    │
   ┌────────────────┴──────────────── obstacle_detector ───────────────────┐
   │                                                                        │
   │  0. приведение СК      lib/frames.py      X вперёд, Y влево, Z вверх   │
   │  1. фильтрация         lib/preprocess.py  рабочая зона, прореживание   │
   │  2. полотно пути       lib/ground.py      профиль высоты по ячейкам    │
   │  3. ось пути           lib/track.py       дуга по рельсам + зона       │
   │                                           доверия                      │
   │  4. коридор габарита   lib/track.py       точки внутри габарита        │
   │  5. свободное место    lib/tunnel.py      граница обделки по полосам   │
   │  6. шум и рельсы       lib/preprocess.py  одиночные точки, нитки       │
   │  7. кластеры и отсев   lib/cluster.py     объекты + причины отбраковки │
   │                        lib/detect.py                                   │
   │  8. скорость носителя  lib/egomotion.py   м/с из сдвига облаков        │
   │  9. треки и решение    lib/tracking.py    N из M кадров, тормозной     │
   │                        lib/decision.py    путь, кинематический гейт    │
   │                                                                        │
   └───────────┬─────────────┬──────────────┬─────────────┬────────────────┘
               │             │              │             │
   /rail_guard/obstacles     │    /rail_guard/track_corridor      │
               │   /rail_guard/gauge_status          /rail_guard/markers
               │             │              │             │
               ▼             ▼              ▼             ▼
        ┌─────────────┐  ┌────────────────────┐  ┌──────────────┐
        │  система    │  │  result_monitor    │  │    RViz 2    │
        │  управления │  │  (терминал, сводка)│  │ (визуализация)│
        │   поездом   │  └────────────────────┘  └──────────────┘
        └─────────────┘
```

Подписки детектора: облако точек и, если есть, `/train/speed`
(`std_msgs/Float32`, м/с). Скорости может не быть — тогда она оценивается по
самим облакам (этап 8), и потребитель видит в `GaugeStatus`, на чём построен
тормозной расчёт: `odometry`, `estimated` или `default`.

## Почему весь тракт в одной ноде

Разбиение по нодам на каждую стадию добавило бы две сериализации облака на
300 тысяч точек в каждом кадре — около половины бюджета реального времени
(8 МБ на сообщение, 10 Гц, два хопа). Промежуточные результаты при этом
доступны снаружи: отладочные облака `points_filtered` и `points_in_gauge`
включаются параметром `publish_debug_clouds`, маркеры коридора и объектов
публикуются всегда.

Замена источника данных не затрагивает обработку: `dataset_player`
воспроизводит записи OSDaR23, `ros2 bag play` — записи метро, драйвер лидара
на поезде публикует в тот же топик.

## Публикуемые топики

| Топик | Тип | Назначение |
|---|---|---|
| `/rail_guard/gauge_status` | `rail_guard_msgs/GaugeStatus` | сводное решение: свободно / внимание / служебное / экстренное, дальность до ближайшей помехи, тормозной путь, дальность подтверждения пути и допустимая на ней скорость, скорость поезда и её источник, обоснование |
| `/rail_guard/obstacles` | `rail_guard_msgs/ObstacleArray` | препятствия кадра: положение, габариты, класс, уверенность, скорость сближения, время до контакта, заход внутрь свободного места; плюс время обработки кадра и число точек |
| `/rail_guard/track_corridor` | `rail_guard_msgs/TrackCorridor` | ось пути, полуширина и высота габарита, радиус кривой, дальность достоверности |
| `/rail_guard/markers` | `visualization_msgs/MarkerArray` | визуализация для RViz |
| `/rail_guard/ego_speed` | `std_msgs/Float32` | скорость, по которой считался тормозной путь |
| `/rail_guard/points_filtered`, `/rail_guard/points_in_gauge` | `sensor_msgs/PointCloud2` | отладочные облака (по параметру) |

Отдельно стоит `max_safe_speed` в `GaugeStatus`: скорость, при которой
тормозной путь укладывается в зону, где положение пути подтверждено
(`confident_range`). Это ограничение по видимости, а не тревога — решение при
свободном габарите остаётся «свободно», а снижать скорость или нет, решает
система управления поездом. Флаг `speed_limited` показывает, что текущая
скорость выше допустимой.

Сообщения самодостаточны: получатель принимает решение, не заглядывая в
облако точек. `ObstacleArray` переводится в `vision_msgs/Detection3DArray`
один в один — поля `centroid`, `size`, `classification`, `confidence`
заполнены для этого.

## Варианты развёртывания

**В контейнере целиком.** Запись проигрывается внутри контейнера, на хосте
не нужен ни ROS, ни зависимости:

```
docker run --rm -v /путь/к/бэгам:/bags:ro rail-guard demo /bags/<запись>
```

**Контейнер как обработчик.** Запись или живой лидар — на хосте, контейнер
только считает. Нужен общий DDS-домен:

```
docker run --rm --network host --ipc host -e ROS_DOMAIN_ID=0 rail-guard detect
ros2 bag play <запись>            # на хосте
```

**Без контейнера.** Собранный воркспейс на машине с ROS 2 Humble:

```
ros2 launch rail_guard_bringup metro.launch.py bag:=<запись>
```

## Где считается

Тракт считает одно и то же на процессоре и на видеокарте: массивы — numpy
или cupy, этапы написаны один раз и принимают модуль массивов аргументом
(`lib/backend.py`). На устройство вынесены три этапа, и только те, что
состоят из поэлементных операций, сортировок и гистограмм — у них нет ни
итеративной логики, ни накопленного состояния:

| Этап | Почему он | Что делает |
|---|---|---|
| фильтрация (`lib/preprocess.py`) | единственный работает с полным кадром — до 920 тыс. точек | маски рабочей зоны, отсечение корпуса, воксельное прореживание |
| свободное пространство (`lib/tunnel.py`) | сетка полос × слоёв по всему кадру | границы свободного места, поддержка слоёв, продольное сглаживание |
| распознавание сцены (`lib/scene.py`) | те же полосы, те же точки | боковые границы, перекрытие, замкнутость |

Оценка полотна, поиск оси, кластеризация и сопровождение остаются на
процессоре сознательно: они итеративны или работают с сотнями точек, и
перенос там дороже счёта.

Три правила этого механизма:

1. **Результат не зависит от устройства.** Воксельное прореживание на
   видеокарте идёт через сортировку, а не через раскладку по таблице: при
   записи в одну ячейку из разных потоков выигрывает произвольный, и
   представитель вокселя менялся бы от запуска к запуску. Совпадение
   проверяется на реальных кадрах — `scripts/check_gpu.py`.
2. **Отказ устройства не останавливает поезд.** Любая ошибка — нет драйвера,
   кончилась память, чужая версия cupy — переводит тракт на процессор
   навсегда, с записью причины в лог и в `GaugeStatus.compute_backend`.
3. **Ничего не переносится «на всякий случай».** Кадр меньше порога
   (`compute.min_points_for_gpu`) считается на процессоре: перенос стоит
   дороже выигрыша.

Выбор задаётся параметром `compute.device` (`auto`, `cpu`, `gpu`), аргументом
запуска `device:=` или переменной `RAIL_GUARD_DEVICE` в контейнере.

## Откуда берутся параметры

Профиль линии (`config/*.yaml`) содержит только то, что нельзя измерить по
облаку точек: габарит подвижного состава, колею, междупутье, минимальный
радиус кривой, тормозные характеристики и размер наименьшего препятствия,
которое система обязана видеть. Это три десятка строк, и все они берутся из
регламента линии, а не из записей.

Всё остальное система определяет сама на ходу:

| Что | Как определяется | Модуль |
|---|---|---|
| ориентация датчика | по геометрии первого пригодного кадра | `lib/frames.py` |
| плотность лучей, дальнобойность | по кадрам, в переднем секторе | `lib/sensor_model.py` |
| тоннель или открытый участок | по непрерывности боковой границы | `lib/scene.py` |
| пороги числа точек, связность | из плотности лучей и размера цели | `lib/derive.py` |
| длина коридора за зоной рельсов | из минимального радиуса кривой | `lib/derive.py` |
| потолок плотности облака | по фактическому времени кадра | `lib/pipeline.py` |

Такое деление — не украшение, а условие переносимости: те же параметры,
заданные числами, означают на другом лидаре и другом участке уже не то, ради
чего их ставили. Любое из выведенных значений можно подавить, задав число в
профиле, — тогда автоматика для этого поля выключается.

## Что где лежит

```
Dockerfile, docker/           сборка и запуск образа
ros2_ws/src/
  rail_guard_msgs/            сообщения
  rail_guard/
    lib/                      алгоритм без зависимости от ROS
      backend.py              выбор устройства: процессор или видеокарта
      report.py               текстовая приборная панель для оператора
      sensor_model.py         измерение датчика: плотность лучей, дальнобойность
      scene.py                распознавание сцены: тоннель или открытый участок
      derive.py               вывод рабочих порогов из физики и измерений
    nodes/                    obstacle_detector, result_monitor, dataset_player
    test/                     51 тест на синтетических сценах и модулях
  rail_guard_bringup/
    launch/metro.launch.py    демонстрация на записи метро
    launch/detector.launch.py только детектор (живой лидар)
    config/metro.yaml         профиль метрополитена (только физика носителя)
    config/mainline.yaml      профиль магистральной линии
scripts/                      офлайн-прогон, метрики, визуализация, видео
  measure_sensor.py           что система измерила о датчике на ваших данных
  check_gpu.py                совпадает ли счёт на видеокарте и насколько он быстрее
docs/                          алгоритм, архитектура, эксперименты, данные
```
